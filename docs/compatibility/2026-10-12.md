## Google consumer support correction

Rechecked Google's primary sources on October 12, 2026. Use `agy` for personal Google-account access; Google supports Antigravity CLI as the consumer replacement for Gemini CLI.

- Google's [May 19 transition announcement](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/) set June 18, 2026 as the cutoff for Gemini CLI requests from free Code Assist individuals and Google AI Pro/Ultra consumers.
- The same announcement preserves Gemini CLI access for Code Assist Standard/Enterprise customers and paid Gemini/Enterprise Agent Platform API keys. Gemini CLI is not globally deprecated; current npm releases do not establish continued consumer OAuth support.
- Google's [July 16 Conductor announcement](https://developers.googleblog.com/evolving-spec-driven-development-conductor-now-supports-antigravity/) explicitly uses `agy plugins install`, confirming the official CLI executable. Local keyless run `20261012T123712-27d8d8c3` returned `OAUTH_OK` with `GEMINI_API_KEY` removed.

The earlier advice to reauthenticate standalone Gemini was wrong for a consumer OAuth workflow. The Gemini API-key probes below verify API integration only. This confirmation changes no adapters, credentials, or security policy.

## Gaps reproduced before the fix

1. **Standalone Gemini is not an out-of-box target.** `python3 bin/yoyo ask gemini --dry-run 'Reply OK'` exits 2 with `Unknown agent 'gemini'`. `bin/yoyo:192` registers Antigravity as `agy`, but no Gemini adapter. `skills/yoyo/SKILL.md:3` and its agent table omit standalone Gemini. Gemini can call yoyo to launch another provider, but yoyo needs a custom adapter to launch Gemini.
2. **The installed CLI cannot run the advertised skill repair.** `yoyo install-skill` on this machine exits 2 with `Bundled skill not found: /Users/sushil/.local/skills`. The installed binary is byte-identical to `bin/yoyo`. `bin/yoyo:5446` looks beside the executable instead of using the source checkout recorded by `install.sh:14`. The initial installer supplies `YOYO_SKILL_SOURCE`, so first installation works; later direct resync does not.
3. **Native skill locations are incompletely covered.** `bin/yoyo:804` searches the shared directory and legacy Google directory, but not `~/.cursor/skills`, `~/.gemini/skills`, or `~/.gemini/antigravity-cli/skills`. The install targets at `bin/yoyo:5322` omit Antigravity CLI's current documented directory. Local Cursor and Gemini already discover yoyo through installed shared/compatibility directories, and Antigravity 1.3.3 still discovers the legacy copy. Those observed fallbacks work; this is path/documentation drift, not a demonstrated discovery failure on this machine.
4. **Doctor hides failures reported on stdout.** The Claude probes report exit 1 with an empty `stderr_snippet`. A real `yoyo ask claude --raw --json` preserved `You've hit your weekly limit · resets 2:30am (Asia/Calcutta)` on stdout. `bin/yoyo:5148` only uses stderr for the failed-probe diagnostic. Doctor should expose a bounded stdout fallback when stderr is empty.
5. **Strict doctor misses a completely absent caller-skill installation.** Running non-live `doctor --strict` with a temporary empty `HOME`, the recorded checkout available, and the real agent binaries on `PATH` returned exit 0 with no missing-skill diagnostic. `bin/yoyo:5414` skips nonexistent installed copies. This should report missing caller guidance without treating shared-directory discovery as a failure.

### Claude read-only safety

`bin/yoyo:1033` restricts built-in tools with `--tools Read,Grep,Glob,LS`. The [current Claude CLI reference](https://code.claude.com/docs/en/cli-reference) explicitly says `--tools` does not affect MCP tools and recommends `--disallowedTools "mcp__*"` to deny them. The flag gap is verified against the command and primary documentation; an MCP write exploit was not attempted, and the quota prevents a live Claude tool check.
